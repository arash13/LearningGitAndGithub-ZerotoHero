# درس ۱.۱ | چرا Git؟ از کپی پوشه تا تاریخچه قابل اعتماد

**هفته:** ۰۱ | **سطح:** صفر مطلق | **وضعیت:** آموزش مفهومی شروع‌شده، آزمون تکمیلی در گفت‌وگو

## مسئله: بدون Git چگونه نسخه‌ها را نگه داریم؟

فرض کن یک پوشه پروژه به نام `MyProject` داری. راه منطقی اول این است که هر بار از کل پوشه یک کپی با تاریخ و ساعت بسازی:

```text
MyProject/
MyProject-2026-11-01-0900/
MyProject-2026-11-02-1800/
MyProject-2026-11-03-1200/
```

این راهکار برای یک پروژه کوچک و یک نفر شروع قابل فهمی است؛ اما با زیاد شدن نسخه‌ها و تغییرات، پیدا کردن **تفاوت دقیق**، **دلیل تغییر** و **نسخه درست برای بازگشت** سخت می‌شود.

## پیشنهاد دوم: نوشتن گزارش تغییرات در یک فایل متنی

راه حل طبیعی دیگر، نگهداری یک گزارش دستی است:

```text
Date: 2026-11-03
Class: Login
Added method: ChangePass
Reason: Allow users to change their password
```

این گزارش اطلاعات مهمی درباره **هدف تغییر** می‌دهد؛ اما درباره خط‌های دقیق تغییرکرده، مقدار قبلی آن‌ها، فایل‌های واقعاً تغییرکرده و تغییرهایی که فراموش کرده‌ای بنویسی ضمانتی نمی‌دهد.

## تفاوت دو نوع اطلاعات

- **چه چیزی دقیقاً تغییر کرده؟** با مقایسه فایل‌ها و نسخه‌ها مشخص می‌شود. در Git به این تفاوت `diff` می‌گوییم.
- **چرا تغییر انجام شده؟** توسعه‌دهنده با پیام توضیحی `commit message` ثبت می‌کند. Git دلیل تصمیم را خودکار تشخیص نمی‌دهد.

### مثال ملموس در کلاس Login

فرض کن در یک نمونه آموزشی از متد `ChangePass` فقط شرط طول رمز را عوض کرده‌ای:

```diff
- if (newPassword.Length < 8) return false;
+ if (newPassword.Length < 12) return false;
```

این خروجی نشان می‌دهد **دقیقاً کدام خط** حذف و کدام خط اضافه شده است. یک پیام ثبت مناسب می‌تواند چنین باشد:

```text
fix(auth): increase minimum password length to 12
```

این مثال صرفاً برای فهم نسخه‌بندی است و پیاده‌سازی کامل یا راهنمای امنیت رمز عبور محسوب نمی‌شود.

## نکته مهم: بازیابی انتخابی دستی هم امکان‌پذیر است

اگر از پروژه نسخه پشتیبان کامل گرفته باشی، برای رفع یک خطا الزاماً تمام پوشه را بازنمی‌گردانی؛ می‌توانی فقط کلاس، متد یا فایل آسیب‌دیده را از نسخه مناسب برداری. این کار در پروژه‌های کوچک گاهی کاملاً عملی است.

محدودیت‌ها معمولاً در مقیاس و اطمینان‌پذیری ظاهر می‌شوند:

۱. باید خودت نسخه مناسب را پیدا و تغییرهای مرتبط را دستی مقایسه کنی.
۲. یک قابلیت ممکن است به چند فایل یا تغییر وابسته باشد؛ بازیابی فقط یک متد می‌تواند ناسازگاری ایجاد کند.
۳. وقتی چند نفر هم‌زمان تغییر می‌دهند، تشخیص اینکه کدام تغییر متعلق به کیست دشوارتر می‌شود.

Git تاریخچه و ابزار مقایسه، بررسی و بازگردانی تغییرات را فراهم می‌کند، اما خودکار تشخیص نمی‌دهد کدام خط باعث باگ شده است. حتی بازگردانی یک Commit گاهی نیاز به حل تعارض دارد و ممکن است روی تغییرات بعدی اثر بگذارد.

## Git چه کمکی می‌کند؟

Git تغییرات فایل‌های تحت کنترل نسخه را می‌سنجد و برای تاریخچه نقاط ثبت‌شده (`commit`) ایجاد می‌کند. هر Commit به وضعیت پروژه در آن لحظه، نویسنده و پیام ثبت مرتبط است. Git همچنین مقایسه دو نسخه ثبت‌شده را فراهم می‌کند.

به جای اینکه خودت تمام نسخه‌های پوشه را نام‌گذاری و مقایسه کنی، از تاریخچه و ابزارهای Git استفاده می‌کنی. **Git جای نسخه پشتیبان مستقل را به‌طور کامل نمی‌گیرد**؛ برای داده‌های مهم همچنان پشتیبان‌گیری لازم است.

## مرزبندی با GitHub

`Git` سیستم کنترل نسخه است و روی دستگاه خودت هم کار می‌کند. `GitHub` سرویس میزبانی مخزن و امکانات همکاری است. ثبت یک Commit محلی لزوماً به معنی انتشار آن روی GitHub نیست.

## آزمون مفهومی درس ۱.۱

۱. اگر فقط در فایل `changes.txt` بنویسی «متد ChangePass را اضافه کردم»، چه اطلاعات مهمی درباره تغییر هنوز مشخص نشده است؟

۲. برای ثبت «دلیل تغییر» و «تغییر خط‌به‌خط»، به ترتیب چه دو نوع اطلاعات نیاز داریم؟

۳. اگر همکار تو همان فایل را در همان زمان تغییر دهد، کپی‌گرفتن پوشه‌ها چه محدودیتی ایجاد می‌کند؟

**تکلیف:** با زبان خودت جواب بده. تا وقتی مفهوم روشن نشده، نیازی به حفظ هیچ دستور Git نیست.
